# 生成メディア自動化パイプライン・プレイブック

**概念 → シミュレーション/レンダー → コンポジット → 公開** を自動化する
パイプラインを設計・運用・デバッグするための、プロジェクト非依存の指針集。

このリポジトリ（chaosim = Blender物理シム → YouTube Shorts）を具体例＝リファレンス実装として
書いているが、原則はレンダラ（Blender / Houdini / Unreal / p5.js / three.js …）や
出力先（YouTube / TikTok / 社内配信）を問わず流用できる。読み替え表を末尾に置く。

---

## 0. このドキュメントの使い方

新しい「入力を作る → 重い計算で素材を作る → 素材を合成する → 配信する」系の自動化を立ち上げるとき、
ゼロから設計判断をやり直さないための土台にする。各章の末尾にチェックリストがあるので、
新規プロジェクトではそれを埋めていけばよい。特に **第6章（コンポジットの落とし穴）** と
**第7章（効果音）** は、実際にハマってから直すと高コストなので着手前に読む価値がある。

---

## 1. アーキテクチャの背骨（抽象形）

パイプラインを**疎結合な段（ステージ）の列**として組む。各段は「入力ファイル群 → 出力ファイル群」を
契約とし、次段は前段の出力ファイルの存在だけに依存する。中間生成物は全部ディスクに残す。

```
plan ──▶ simulate/render ──▶ material(overlay/graphics) ──▶ compose ──▶ finish ──▶ publish
 │            │                     │                          │           │          │
concept.yaml  frames/clip.mp4       overlays/*.(webm|mov|png)  final.mp4   normalized  URL
```

原則:

- **1段 = 1責務。** 段はCLIサブコマンド（`plan` / `render` / `compose` / `upload` …）として個別に叩ける。
  全通しコマンド（`run --stages ...`）は各段を順に呼ぶ薄いオーケストレータにすぎない。
- **外部ツールはサブプロセスとして駆動する。** Blenderも、HTML→動画レンダラも、ffmpegも、
  自前コードから `subprocess` で叩く「重い純粋関数」として扱う。プロセス境界がクラッシュを封じ込める。
- **中間生成物は捨てない。** `renders/` `material/` `work/` `final/` に段ごとの出力を残すと、
  途中から再開でき、不具合の切り分けが「どのファイルまで正しいか」に還元される。
- **秒で時間を持つ。** 段をまたぐタイミング情報（イベント時刻、オーバーレイの開始位置）は
  フレーム番号ではなく**秒**で持つ。fps が段ごとに違っても壊れない（sim 30fps + overlay 60fps でも合う）。

### スタブ・フォールバックという設計思想（重要）

各外部ツールは「無ければ ffmpeg 等の簡易版に自動降格」させる。こうするとパイプライン全体が
**ffmpeg だけで最後まで完走**でき、CI・サンドボックス・新環境で常に緑になる。
「本物のツールがあるか」を実行時に判定（`*_available()`）し、無ければスタブ経路へ。
`STUB=1` / `--preview` で強制降格もできるようにしておく。品質は落ちるが**配線は常に検証される**。

> リファレンス実装: `pipeline/workflow.py`（段の列）、`pipeline/hyperframes.py`（`hyperframes_available()` →
> 本物 or ffmpegスタブ）、`scripts/chaosim.py`（段ごとのCLIサブコマンド）。

**立ち上げチェックリスト**
- [ ] 段を列挙し、各段の入力/出力ファイル契約を1行で書けるか
- [ ] 各段を単体で叩けるCLIがあるか
- [ ] 外部ツールごとに `available()` 判定とスタブ経路があるか
- [ ] 段間のタイミングは秒で持っているか
- [ ] 中間生成物が段ごとにディスクに残るか

## 2. フェーズ制とゲート（品質と計算コストの両立）

重いレンダーを回す前に、**安いテストで意図を確定**させる。段の中に「安全に上流に戻れる関門」を置く。

```
concept ─▶ vertical slice(低解像度・数フレーム) ─[GATE]─▶ 本番レンダー ─▶ 展開 ─▶ 仕上げ
```

- **バーティカル・スライス**: カメラ・マテリアル・構図だけを低解像度＋数フレームで確認する試写。
  ここを通過するまで `medium/high/ultra` の本番レンダーを**回さない**。1本の失敗コストを桁で下げる。
- **ゲートは人間 or 自動チェックの通過点**。「主役が画角に入っているか」「色が破綻していないか」を
  1フレーム抜いて確認するだけでよい（第8章の frame-sampling 検証）。
- **プリセット階層**を用意する: `preview`(捨て) / `medium`(比較) / `high`(本番) / `ultra`(保存)。
  同じ concept を解像度・サンプル数だけ替えて回せるようにする。

> リファレンス実装: `docs/production-plan.md`、`config/render_presets.json`。

## 3. 分割レンダーとクラッシュからの再開

長いレンダーは**必ず落ちる**前提で設計する。復旧可能性を最初から作り込む。

- **ステージ/セグメント分割**: 比較動画なら「1ステージ = 1サブディレクトリ（連番フレーム）」に分け、
  各ステージを独立に `seg_*.mp4` へエンコード → 最後に concat。1ステージが落ちても他は無傷。
- **冪等な連番出力**: フレームは `frame_%04d.png` でステージ別ディレクトリに吐く。既存フレームは
  再実行でそのまま使え、**未完のステージだけ**焼き直せる。
- **物理シムの再開は「再ベイクしてから欠損フレームだけ描画」**。物理キャッシュは連続性が要るので、
  途中フレームだけを単発描画するには、そのステージを**丸ごと再ベイク**してから欠損レンジを描く。
- **壊れフレームを疑う**: クラッシュ直前に書きかけの PNG が残ることがある。再開時は各フレームを
  デコード検証（`ffmpeg -v error -i frame.png -f null -`）し、壊れていれば描き直す。
- **重い処理はバッチ＋非ブロッキング**: レンダーは 30〜50 フレーム単位のバッチに割り、
  タイムアウトを避ける。数分かかる全通しは**バックグラウンド起動＋ログファイルをポーリング**して進捗を見る。

**再開チェックリスト**
- [ ] 出力はステージ別・連番で、部分的に再実行できるか
- [ ] 各ステージの「完了 = Nフレーム揃っている」を機械的に判定できるか
- [ ] 壊れフレームのデコード検証をしてから結合しているか
- [ ] 長時間処理はバッチ化 or バックグラウンド化してあるか

## 4. コンポジション層 — HTMLグラフィックをオーバーレイする

タイトル・ラベル・カウンタ・下三分の一・アウトロといった**動くグラフィックは HTML/CSS/JS で作り、
透過動画としてレンダーして本編に重ねる**のが移植性・再利用性ともに高い。

### 標準契約（テンプレートの型）

- ルートに1つの合成対象 `<div data-composition-id="main" data-duration="N">` を置く。
- アニメーションは**ポーズ済みのタイムライン**（例: GSAP）を1つだけ登録する
  （`window.__timelines["main"]`）。レンダラはこれを時間駆動でコマ送りする。
- テンプレートは `_base` を継承し、`style` / `body` / `timeline` ブロックだけを差し替える。
  透過フラグを受け取り、`background: transparent` を切り替えられるようにする。

### オーバーレイ = 「別トラックの透過クリップ」として合成

- 各グラフィックを**全画面サイズの透過クリップ**（数字は上部にCSSで配置、他は透明）として吐き、
  ffmpeg `overlay=x=0:y=0:eof_action=pass` で本編に時間差合成する。
- タイミングは concept 側のセグメント定義（`track: overlay`, `start`, `duration`, `text` …）で宣言する。
  段のコードではなく**データで**オーバーレイの内容と位置を決める（再利用性が上がる）。

> リファレンス実装: `templates/hyperframes/*.j2`（`_base` 継承＋3ブロック）、
> `pipeline/compositor.py`（`overlay_segment`）、`concepts/cloth_by_faces.yaml` の `segments:`。
> 今回、面数カウント（16→64→256→1024）をこの仕組みで実装した。

## 5. 横断的なエンジニアリング作法

- **サンドボックスとホストはファイルシステムが別。** コード実行環境（Linuxサンドボックス等）と
  実ツールが動くホスト（macOS等）でパスが違う。ホスト上のツールに渡すパスは**ホストのパス**で。
  合成用の ffmpeg 処理はマウント済みの成果物を読める側で回すと速い。
- **ヘッドレス/GUI 経由のサブプロセスは PATH が貧弱。** GUIアプリや非対話シェルから起動した
  サブプロセスは、普段のターミナルの PATH（nvm の node、homebrew の ffmpeg 等）を持たないことがある。
  **ログインかつ対話シェル**（`zsh -l -i -c`）で起動して PATH を揃えるか、必要バイナリを絶対パスで渡す。
  今回、node/ffmpeg が見つからずスタブに落ちて失敗 → 対話ログインシェル起動で解決した。
- **クロスプラットフォームのネイティブ依存に注意。** node_modules 等はビルド先アーキテクチャに紐づく
  （例: `sharp` が macOS 版だと Linux サンドボックスで動かない）。**本物のレンダーはホストで**回す。
- **検証は「1フレーム抜いて見る」。** 各ステージの中間時刻を1枚PNGに書き出し、横に並べたモンタージュを
  目視する。動画を最後まで見なくても、主役・オーバーレイ・色・タイミングの破綻が一目で分かる。

## 6. コンポジットの落とし穴（実際に踏んだもの＝再利用価値大）

透過オーバーレイ周りは環境依存の罠が多い。汎用の教訓として残す。

| # | 症状 | 原因 | 対処 |
|---|---|---|---|
| 1 | 透過レンダーが即エラー | HTML→動画レンダラが「アルファ出力（webm/mov/png連番）」と「出力解像度プリセット」の**併用を禁止** | 透過時は解像度プリセットを付けない。コンポジション自体に `data-width/height` を持たせて原寸で出す |
| 2 | 合成すると背景が**真っ黒**、数字だけ見える | webm(VP9)にアルファはある（`ALPHA_MODE=1`）が、**ffmpeg 既定の vp9 デコーダがアルファ面を捨てる** | オーバーレイ入力に `-c:v libvpx-vp9` を**明示**してデコードする |
| 3 | 透過のはずが不透明な黒背景 | テンプレートに透過フラグが渡らず `background` がブランド色（黒）にフォールバック | 透過フラグを必ずテンプレコンテキストに入れ、`background: transparent` を確認。**赤背景に重ねて赤が透けるか**でアルファを実測する |
| 4 | 段間で解像度/フレームレートがバラつく | sim 30fps・overlay 60fps・アウトロ別素材、をそのまま結合 | concat/overlay 前にサイズ・fps・SAR を正規化。タイミングは秒基準なのでズレない |

**アルファの実測テスト（環境非依存の確認法）**
```bash
# 透過クリップを赤ベタに重ね、空き領域のピクセルが赤(≈252,0,0)なら透過OK、黒(0,0,0)ならNG
ffmpeg -f lavfi -i color=c=red:s=WxH:d=1 -c:v libvpx-vp9 -i overlay.webm \
  -filter_complex "[0:v][1:v]overlay" -frames:v 1 -f rawvideo -pix_fmt rgb24 - \
  | tail -c 3 | od -An -tu1
```

> 教訓: **「アルファ・メタデータがある」≠「合成で透ける」。** 必ず実合成で1ピクセル確認する。
> 迷ったら webm(VP9)ではなく **MOV(ProRes 4444) か PNG連番**の方がアルファは安定する。

## 7. 効果音（SFX）の合成 — ここが一番難しい

物理シム系ショートの生命線は「動きと音の一致」。**音が最大の難所**なので独立章にする。
（本文の詳細版は `docs/sfx-design.md`。ここではプロジェクト横断の論点として抽象化する。）

### なぜ難しいのか

映像は「概念→計算→合成」で決定論的に作れるが、SFX は **(a) 正確なタイミング**、**(b) 適切な音源**、
**(c) 自然なばらつき**、**(d) 帯域のすみ分け（ミックス）** の4つを同時に満たす必要がある。
どれか1つでも欠けると「汎用的でズレた安っぽい音」になり、満足感が一気に崩れる。

### 現状の枠組み（正しい）

イベント時刻JSON → キュー割り当て → ffmpeg でミックス、の3段は方向として正しい。
固定アンカー（intro/sim/outro）と、シム由来の衝突イベント（`<slug>_events.json`）の両系統を持つ。

### 論点（=どのプロジェクトでも噴出する課題）

| # | 課題 | 影響 |
|---|---|---|
| 1 | **音源がOS/環境依存**（例: macOS システム音） | 他環境で鳴らない・ライセンス/収益化が不安 |
| 2 | **イベント出力が一部シーンのみ** | 衝突が定義されていないシーンに音が付かない |
| 3 | **1イベント=1音の使い回し** | 同じ音の連打で機械的（マシンガン化） |
| 4 | **強度情報がない**（時刻と種別だけ） | 大小の衝突が同じ音量になり抑揚が出ない |
| 5 | **レイヤーがない**（単発音のみ） | 実物の「アタック＋ボディ＋低域の余韻」に比べ軽い |
| 6 | **ダッキング/正規化なし** | BGMが音を潰す or 全体が刺さる。配信ラウドネス基準（-14 LUFS）未対応 |
| 7 | **同期の保証が弱い** | イベントを本番と別ベイクで出すと初期値がズレる恐れ |

### 抽象的な解（推奨アプローチ）

1. **タイミングは計算が決める（手打ちしない）。** イベントは**本番と同じベイク/シミュレーション**から
   吐く。時刻は秒で fps 非依存に。別ベイクは「確認専用」に留める（同期の担保）。
2. **イベントを型＋強度付きに拡張。** `{t, type, intensity, object}` を標準スキーマにする。
   `type`（impact/drop/collapse/whoosh/settle …）と `intensity`(0–1) を音源選択・音量・低域量にマップ。
3. **音源はライブラリから“役割”で引く。** ロイヤリティフリー音源を役割別ディレクトリ＋カタログで管理し、
   OS 依存音は**フォールバックに降格**。「型 → 役割 → 実ファイル」の間接参照にする。
4. **1発ごとに揺らす。** ラウンドロビン＋ピッチ/音量の微ランダム（`asetrate`）＋ポリフォニー制限
   （近接イベントの間引き）でマシンガン化を防ぐ。
5. **重ねる。** 大きい衝突は本体＋低域レイヤー（rumble）で重量感を出す。
6. **BGMを踏む。** 効果音・ナレの瞬間だけ**サイドチェイン・ダッキング**（`sidechaincompress`）でBGMを下げる。
7. **最後に揃える。** 書き出し最終段で `loudnorm=I=-14:LRA=11:TP=-1.5` に正規化する。

### 代替戦略（環境で選ぶ）

- **A データ駆動＋SFXライブラリ**（日常の量産）— 上記1〜7。
- **B プロシージャル合成**（音源を持ち込めないCI/自動フォールバック）— 衝突音を都度合成、ライセンス完全クリア。
- **C 手作業DAW**（勝負回のヒーロー動画）— 自動化しない最高品質。
- **D 外部SFX生成API/MCP**（将来拡張）— イベントの `type/intensity` をそのままプロンプト化して生成音を取得。

カタログに音源があるかで A↔B を自動分岐させる（スタブ思想と同じ）。

### 最小差分で効果が大きい着手順

1. 最終エンコードに `loudnorm` を1行追加（全動画が即改善）
2. イベントに `intensity` を足して音量にマップ
3. 1発ごとのピッチ/音量ランダム＋ポリフォニー制限
4. ロイヤリティフリー音源＋カタログを用意し OS 音から移行
5. BGM サイドチェイン・ダッキング
6. イベント出力を全シーンへ展開

## 8. 汎用チェックリスト（新規プロジェクトのブリングアップ）

- [ ] `STUB`/`--preview` で強制降格できる

**品質ゲート**
- [ ] 低解像度スライス → ゲート → 本番、の流れがある
- [ ] `preview/medium/high/ultra` のプリセット階層

**堅牢性**
- [ ] 分割レンダー＋部分再実行＋壊れフレーム検証
- [ ] 長時間処理のバッチ化/バックグラウンド化＋ログポーリング

- [ ] グラフィックは HTML テンプレ＋透過クリップ＋データ駆動オーバーレイ
- [ ] 透過は「赤背景に重ねて実測」で検証済み（アルファ・メタだけを信じない）
- [ ] 段間のサイズ/fps/SAR 正規化、タイミングは秒基準

**音**
- [ ] イベントは本番ベイク由来・型＋強度付き
- [ ] 音源はライブラリから役割引き（OS音はフォールバック）

**環境**
- [ ] ホスト/サンドボックスのパス差を把握
- [ ] サブプロセスの PATH をログイン対話シェル or 絶対パスで担保
- [ ] ネイティブ依存（node_modules 等）は実行アーキテクチャに合わせる

## 付録: 一度ハマったら思い出したい3行

1. **透過は実測せよ** — アルファのメタがあっても合成で透けるとは限らない（`-c:v libvpx-vp9` / 赤背景テスト）。
2. **PATHはログイン対話シェルで** — GUI/非対話サブプロセスは node・ffmpeg を見失う。
3. **1フレーム抜いて並べよ** — 動画を最後まで見ずに、モンタージュで破綻を一目確認。
